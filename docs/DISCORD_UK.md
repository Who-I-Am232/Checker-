# Сповіщення в Discord

Для повідомлень як від бота достатньо **webhook каналу**. Окрему Discord
application, bot token, OAuth-запрошення та Gateway intents створювати не потрібно.
Скрипт `notifier/discord_bot.py` надсилає повідомлення з назвою ConflictAudit.
Команд і кнопок адміністрування у цій версії немає.

## 1. Створити webhook

1. Відкрийте приватний текстовий канал для адміністрації.
2. **Налаштування каналу → Інтеграції → Webhooks → Створити webhook**.
   Для цього потрібен дозвіл керування webhooks.
3. Оберіть канал та аватар, скопіюйте Webhook URL. Скрипт задає ім'я повідомлень
   `ConflictAudit`; аватар можна налаштувати у Discord.
4. Збережіть URL у змінній середовища машини з notifier. Це секрет, який дає
   право надсилати повідомлення в канал: не додавайте його в git, скриншоти чи чат.

Приймається HTTPS URL домену `discord.com` з `/api/webhooks/...` або
`/api/v10/webhooks/...`; optional `thread_id` підтримується. Скрипт додає
`wait=true`, щоб отримати підтвердження з ID повідомлення. Redirect не виконується.

## 2. Перевірити вигляд без Discord

Python 3.10+, сторонні бібліотеки не потрібні. З кореня репозиторію:

```bash
python3 notifier/discord_bot.py --input examples/alerts-movement.jsonl --server-id server-1 --server-name "Server 1"
```

Без `--send` скрипт лише друкує Discord payload: мережевих запитів, читання
webhook-секрету чи змін SQLite немає. Приклад повідомлення зі штучними даними:

```text
Server 1
[VEHICLE] DemoDriver
[synthetic-player-7]
Підозріле переміщення / можливий телепорт
authorization=UNVERIFIED
distance=702.195 m; time_delta=1 s
AVG_SPEED=702.195 m/s; INST_SPEED=145.189 m/s
Звідки: 100, 10, 200
Куди: 802.195, 10, 200
UTC: 2026-11-11T09:01:10+00:00
Alert: 6c6a955ee76c8e421657
Потрібна перевірка адміністратора. Це не доказ використання читів.
Зазначено персонажа/водія; причина переміщення невідома.
```

Інші правила також надсилаються: створення об'єктів, групові вибухові
пошкодження, тригери, watchlist і втрата телеметрії. Для невстановленого автора
повідомлення показує «Гравця не встановлено». Ніки очищуються від керувальних
символів, Markdown екранується, `allowed_mentions.parse=[]` вимикає згадки.

Спавн техніки, споруд та інших об'єктів використовує той самий порядок:
сервер → `[тип] гравець` → `[UID]` → причина → виміри. Змішана група має тип
`[MIXED]` і окремі кількості VEHICLE/BUILDING/ENTITY. Приклад споруд:

```text
Server 1
[BUILDING] Гравця не встановлено
[UID невідомий]
Підозрілий спавн: шлях створення не встановлено
authorization=UNVERIFIED
count=6; time_delta=0.5 s; window=10 s
VEHICLE=0; BUILDING=6; ENTITY=0
OBSERVED_RATE=12 /s
route_unknown=6; actor_unknown=6
Prefab: {DEMO}Prefabs/Structures/TestWall.et × 6
Координати: 320, 0, 20
```

Нижче додаються UTC, alert ID та позначка ручної перевірки. `time_delta` —
фактичний час між першим і останнім спостереженнями групи, `window` — задане
вікно правила. За нульового delta швидкість потоку позначається `н/д`.
Це кількість спостережених об'єктів, не доведена кількість незаконних spawn.

Для callback, пов'язаних із кількома гравцями, показується кількість об'єктів
кожного гравця; загальна кількість не приписується кожному окремо. `route_unknown`
означає невстановлений інструментований маршрут, `actor_unknown` — відсутність
надійного зіставлення з автором. Для spatial_changes лишається застереження про
можливі рух/streaming. Старі alerts без нових metrics підтримуються з `н/д`.

Перегляд усіх чотирьох типів:

```bash
python3 notifier/discord_bot.py --input examples/alerts-spawn.jsonl --server-id server-1 --server-name "Server 1"
```

Підтверджені GM-дії мають заголовок «Підтверджена дія Game Master / адміністратора»,
`role=ADMIN` або `role=GAME_MASTER`, `authorization=GM_AUTHORIZED`. Роль без
перевірки конкретної дії не змінює підозрілий статус. Для джерела, лише створеного
GM, показується `GM_ORIGIN`; це не дозвіл на всі наступні ефекти. Докладніше:
[ADMIN_ACTIONS_UK.md](ADMIN_ACTIONS_UK.md). Усі повідомлення використовують той
самий webhook. Пороги визначають, коли надсилати повідомлення, тому одинична
звичайна GM-дія може бути лише в raw-журналі.

## 3. Запустити живий потік

Спочатку налаштуйте [мод і аналізатор](INSTALL_UK.md). Аналізатор повинен
записувати alerts у режимі `--follow`. Notifier запускається окремим процесом,
може чекати появи вхідного файлу, має вихідний HTTPS-доступ до Discord.

Linux / Bash — URL вводиться приховано і не потрапляє у текст команди:

```bash
read -rsp 'Discord webhook URL: ' DISCORD_WEBHOOK_URL
export DISCORD_WEBHOOK_URL
python3 notifier/discord_bot.py --input runtime/alerts.jsonl --server-id server-1 --server-name "Server 1" --state runtime/discord-server-1.sqlite3 --send --follow
```

Windows / PowerShell:

```powershell
$secret = Read-Host 'Discord webhook URL' -AsSecureString
$env:DISCORD_WEBHOOK_URL = [System.Net.NetworkCredential]::new('', $secret).Password
py -3 notifier/discord_bot.py --input runtime/alerts.jsonl --server-id server-1 --server-name "Server 1" --state runtime/discord-server-1.sqlite3 --send --follow
```

`Ctrl+C` зупиняє процес, черга лишається в SQLite. Для постійного запуску
використайте systemd/Task Scheduler з цими ж аргументами та змінною середовища.
`.env` автоматично не завантажується: змінну має передати shell або service manager.
Для іншої назви змінної є `--webhook-env`, її значення не потрібно передавати
через аргументи командного рядка.

Без `--follow`, але з `--send`, виконується **одна ітерація**: читається до 1000
рядків і відправляється не більше одного готового повідомлення. Exit code 3
означає, що залишились queued/failed записи; для безперервного спорожнення
черги й повторних спроб використовуйте `--send --follow`. Код 2 означає
помилку конфігурації/читання/БД або зупинку через недоступний webhook.

## Кілька серверів

Для кожного сервера запустіть власні аналізатор і notifier з окремими вхідним
файлом та SQLite. Наприклад, `server-1` / `Server 1` та `server-2` / `Server 2`.
Ключ `--server-id` має бути унікальним і незмінним між перезапусками. Відображувану
назву `--server-name` можна змінити; вже поставлені в чергу payload не зміняться.
Різні змінні webhook дозволяють вибрати різні канали. Один webhook також може
отримувати повідомлення від кількох серверів; його спільний ліміт може збільшити
затримку, і кожен процес окремо обробляє отримані 429.

## Черга, повтори та відновлення

- SQLite атомарно зберігає offset вхідного файлу та повідомлення. Читаються
  лише рядки із завершальним `\n`, максимум 64 KiB кожен.
- `(server-id, alert_id)` запобігає повторній постановці в чергу, включно з
  replay аналізатора після перезапуску. Зберігайте той самий файл БД.
- До 10000 queued записів на server-id. При заповненні читання зупиняється
  перед незбереженим записом і поновлюється, коли звільниться місце.
- `wait=true` і message ID потрібні для статусу sent. Network/5xx отримують
  backoff до 300 с; 429 — затримку не меншу за `retry_after`/`Retry-After`.
  Заголовки `X-RateLimit-Remaining` та `X-RateLimit-Reset-After` теж враховуються.
  Власна пауза мінімум 1 с не вважається гарантованим лімітом Discord.
- 401/403/404 або redirect зупиняють процес, черга зберігається. Виправте URL,
  доступ до каналу чи webhook і перезапустіть. До повторної спроби діє пауза
  щонайменше 300 с, що запобігає частим помилковим запитам.
- Інші постійні 4xx лишають повідомлення зі статусом failed та кодом помилки,
  виводиться попередження. Після усунення причини адміністратор може зупинити
  notifier, перевірити payload і повернути потрібний запис у queued через SQLite.
- Для одного input/server-id запускайте один робочий процес. Lease на 60 с
  захищає повідомлення від одночасної обробки при випадковому другому запуску.

Після збою між прийняттям повідомлення Discord і записом sent можливий повтор:
webhook не дає спільної транзакції з локальною SQLite. `alert_id` у повідомленні
дозволяє його розпізнати; гарантії exactly-once немає.

Зберігайте alert-файл, доки всі потрібні записи не потрапили в чергу. Новий inode,
скорочення файлу або змінений checkpoint викликають повторне читання з
дедуплікацією. Для роботи append-only надійніший, ніж copy-truncate: перезапис
вже прочитаного середнього фрагмента зі збереженим checkpoint може лишитися
непоміченим. Не підміняйте input під час активного читання.

Статуси видно SQLite-запитом `SELECT status, COUNT(*) FROM alerts GROUP BY status;`.
У sent очищується payload, але ID зберігається для дедуплікації. Тому БД з часом
росте: контролюйте диск і резервуйте її SQLite backup API або після зупинки
процесу. Видалення БД/ID та replay старих alerts може надіслати їх повторно.
Некоректний JSON/завеликий рядок зупиняє читання без мовчазного пропуску запису.

Discord отримує імена, UID, координати й виміри з вибраного alert; повний raw
журнал не відправляється. Доступ до каналу й локальних файлів залиште адміністрації.
Перевірки доставки виконані з підставним HTTP-транспортом; **реальний webhook
у цьому середовищі не налаштовано і повідомлення в Discord не надсилалися**.
