# Встановлення та запуск

## 1. Зібрати addon

Потрібні Arma Reforger Tools / Workbench, базова гра та окремий тестовий dedicated
server тієї самої версії. У середовищі розробки цього прототипу їх немає, тому
компіляція Enforce і запуск гри ще не виконані.

У Workbench додайте/відкрийте `mod/ConflictAudit/ConflictAudit.gproj`. Проєкт залежить
лише від базового Arma Reforger (`58D0FB3206B6F859`). Відкрийте Script Editor,
перекомпілюйте скрипти та виправте будь-яку відмінність API саме вашої версії,
звіряючись із [API_SOURCES.md](API_SOURCES.md). Якщо Workbench вимагає свої
метадані проєкту, створіть New Addon з базовою грою як залежністю і перенесіть у
нього каталог `Scripts`. Це також правильний шлях для отримання власного GUID.

У `gproj` задано конфігурації PC і HEADLESS для першого стенду. Console/crossplay
пакування в цьому прототипі не перевірялося; для нього використайте метадані,
згенеровані поточним Workbench, і окремий тест на потрібних платформах.

Addon містить `modded class`, тому додавання нового компонента на карту не
потрібне. Старт відбувається через `SCR_BaseGameMode.OnGameStart`. Сценарій, який
обходить цей клас або не викликає `super`, потребує окремої інтеграції.

Для локального запуску підключіть проєкт засобами Workbench/Peer Tool чи через
локальний addon workflow вашого dedicated server. Для розповсюдження звичайним
серверним `game.mods` спершу потрібно опублікувати addon через ваш Workbench і
отримати **реальний Workshop ID**. Локальний GUID із цього репозиторію не можна
вважати вже доступним модом для автоматичного завантаження.

Публікацію Workshop і зміну бойового сервера тут не виконано. Репозиторій містить
усі підготовлені вихідні файли та інструкції для цих кроків.

## 2. Перевірити телеметрію

Dedicated server повинен мати доступ до запису у свій profile. Після запуску
Conflict перевірте каталог `ConflictAudit` усередині цього profile:

```text
events-<unix>-<tick>-<random>-0.jsonl
events-<unix>-<tick>-<random>-1.jsonl
...
```

Очікуються `session_start` та приблизно один `heartbeat` за 10 секунд, плюс час
очікування в черзі. Перші 60 секунд позначаються `warmup`: події записуються,
але поведінкові правила аналізатора їх не оцінюють. Довге відновлення persistence
потребує більшого `STARTUP_GRACE_MS` і повторної компіляції.

Виконайте контрольні дії після warmup: штатне будівництво, встановлення/підрив
заряду та вибух із пошкодженням тестового об'єкта. Перевірте raw JSONL, а не лише
наявність alert: невелика штатна дія може не перевищувати жоден поріг.

## 3. Запустити аналізатор

Python 3.10+, без `pip install`. З кореня репозиторію:

```bash
python3 analyzer/checker.py --input /absolute/path/profile/ConflictAudit --config config/analyzer.json --output runtime/alerts.jsonl --follow
```

Windows PowerShell, приклад шляху:

```powershell
py -3 analyzer/checker.py --input "D:\ReforgerProfile\ConflictAudit" --config config/analyzer.json --output runtime/alerts.jsonl --follow
```

Результат записується в JSONL і в термінал. `Ctrl+C` завершує live reader. Для
одноразового аналізу приберіть `--follow`: у такому режимі вихідний файл
перезаписується, а незавершені кореляції завершуються наприкінці вхідних даних.
Використовуйте повний фрагмент сесії: обрізання логу до останнього callback може
створити хибне спрацювання невідомого маршруту.

`--follow` читає закінчені рядки та підхоплює нові файли ротації. Незакінчений
останній рядок очікує наступного запису. Через 45 секунд без нових рядків
з'являється попередження; якщо попередня подія відома — також `collector_silent`.
Це повідомлення про стан збору даних, не про гравця. Перезапуск live reader
повторно читає доступні файли: offsets не зберігаються між запусками, тому alerts
можуть повторитися. `alert_id` детермінований; при зовнішньому імпорті робіть
dedup за цим полем. Читання очікує порядок `seq` усередині кожної сесії.

## 4. Калібрування

Пороги в `config/analyzer.json` змінюються без перекомпіляції мода, після
перезапуску аналізатора. Початкові правила працюють у клітинках 150 × 150 м:

| Правило | Стартовий поріг | Значення |
|---|---|---|
| `spawn_burst` | 12 об'єктів / 10 с | Включає відомі маршрути будівництва |
| `unattributed_spawn_burst` | 6 об'єктів / 10 с | Немає зіставленого інструментованого маршруту |
| `spatial_changes` | 8 нових спостережень / 10 с | Нижча впевненість: можливі рух або streaming |
| `explosive_trigger_burst` | 6 різних пристроїв / 5 с | Виклики UseTrigger, не всі вибухи рушія |
| `explosive_damage_cluster` | 8 різних пошкоджених об'єктів / 2 с | Це кількість цілей, не кількість вибухів |

Повтор однакового правила в тій самій клітинці пригнічується на 30 секунд.
Пороги не враховують конкретні артилерійські/будівельні моди вашого сервера.
Порівняйте їх із нормальними боєм, будівництвом і GM-сесією. Не додавайте до
винятків усіх адміністраторів: облікові записи та легальні інструменти також
можуть використовуватися неналежно.

`allowed_prefabs` — точні ResourceName з журналу, для яких вимикаються правила
появи об'єктів; raw-події залишаються. `watch_prefabs` — точні назви prefab, які
треба позначати навіть по одному. Порожні списки — без винятків і без watchlist.
Зазначення нового рядка в `known_routes` саме по собі не додає ігрового сенсора:
для стороннього будівельного мода потрібен адаптер після успішного серверного
створення об'єкта, який викликає `ObserveAction` з перевіреним джерелом гравця.

## 5. Навантаження і зберігання

У `CA_Settings` задано: tick 1 с, максимум 1024 queued-події, до 256 записів за
звичайний tick, один просторовий запит за tick, 64 кешовані ділянки. Запит
переривається після 2000 callback або після спостережуваних 3 мс. Це **best effort**:
не охоплює витрати native broadphase до callback і не гарантує загальний час tick.
У щільній забудові можливі `scan_incomplete`, а отже відсутність покриття сканером.

Вимірюйте `-logStats 10000` до/після за однакової кількості гравців, AI та техніки.
Якщо сканер погіршує серверний FPS, зменште площу/ліміти або вимкніть
`SCANNER_ENABLED`, залишивши подієві сенсори, і зафіксуйте зміну покриття.

Журнал пишеться пакетами та закривається після flush. Аварія може втратити чергу
та непідтверджені дискові записи. Файли ротуються приблизно по 8 MiB, максимум
8 файлів на сесію. Після цього збір **зупиняється** з `AUDIT STOPPED` у звичайному
лозі; він не перезаписує старі докази. Це обмеження на одну сесію, не на весь
каталог: архівуйте попередні сесії та контролюйте вільне місце. Аналізатор приймає
до 512 файлів за один прохід. Окремі server profiles мають окремі каталоги.

Зберігайте raw JSONL разом із alerts. Експорт/резервне копіювання організуйте
засобами адміністратора. Прототип не має криптографічного захисту журналу і не
передає його за межі хоста самостійно. У git не потрібно додавати бойові журнали,
паролі, RCON-конфігурацію чи дані гравців.
