# Формат даних: schema 1

Один JSON-об'єкт на рядок, UTF-8. Серіалізація імен виконується JSON serializer,
а не конкатенацією довільного тексту в JSON. Переноси рядків у рядкових значеннях
екрануються. Повний набір прикладів: `examples/events-demo-0.jsonl`.

| Поле | Значення |
|---|---|
| `session`, `seq` | ID запуску колектора та порядковий номер записаного спостереження |
| `t_ms`, `utc` | Мілісекунди від старту колектора, Unix UTC секунди події |
| `kind`, `source` | Тип спостереження та сенсор/маршрут |
| `entity`, `parent` | Ідентифікатори об'єктів у межах цієї сесії, не глобальні GUID |
| `prefab`, `category` | ResourceName і тип editable-об'єкта або UNCLASSIFIED |
| `x`, `y`, `z` | Світові координати в метрах; Y — висота |
| `actor_id` | Повідомлений session player ID, 0 — невідомий |
| `actor_uid`, `actor_name` | Тільки коли доступне доречне серверне зіставлення; можуть бути порожні |
| `attribution` | unknown, server_action_callback, engine_instigator, identity_only |
| `source_entity` | ID джерела damage, якщо наданий контекстом |
| `amount` | damageValue контексту, не гарантована остаточна втрата health |
| `count` | Лічильник для heartbeat/baseline/втрати даних |
| `warmup` | Подія в початковому вікні відновлення |

`entity_init` — ініціалізація компонента, не універсальний доказ нового spawn.
`placement` — спостережуване завершення штатного розміщення. `scan_new` — об'єкт,
якого не було в попередньому повному знімку. `explosive_trigger` — виклик
UseTrigger, не підтвердження кожного фактичного вибуху. `explosive_damage` —
callback damage manager для EDamageType.EXPLOSIVE, іноді багато callback на ціль.

Один вибух може пошкодити багато об'єктів і hitzone. Правило damage рахує різні
`entity` у вікні, а не рядки і не кількість вибухів. Тригери так само
дедуплікуються за пристроєм. Це консервативний підрахунок: повторна шкода тій
самій цілі у вікні не збільшує кількість різних цілей.

Усі поля alert наведено в `examples/alerts-demo.jsonl`. `evidence_seq` обмежено
64 номерами, `samples` — 8 прикладами. Повний raw-файл залишається джерелом
розслідування. `reported_actors` може містити кількох гравців із різних подій
групи; це не означає, що кожен із них одноосібно перевищив поріг.

Файли потрібно читати по порядку сесії й part, рядки — по `seq`. Старі/повторні
`seq` у межах сесії пропускаються. Відсутні номери створюють `sequence_gap`.
Формат не призначений для приймання довільних клієнтських повідомлень: аналізатор
має отримувати лише журнал встановленого серверного колектора. Підроблений
server-side файл може підробити будь-яку записану атрибуцію.
